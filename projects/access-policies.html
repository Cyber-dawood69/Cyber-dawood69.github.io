When an Allow
isn’t enough.

Testing how identity permissions, a bucket policy and a permissions boundary affect S3 uploads.

GUIDED AWS BUILDER LABCOMPLETED 22 SEP 2026

The problem

An EC2 workload role initially allowed uploads of four named text files into two lab buckets. I needed to verify those permissions, then observe what changed when a resource policy and permissions boundary were applied.

My investigation

  1. Inspected the role's S3 policy. Listing buckets, listing objects and uploading objects were separate permissions; listing a name did not establish permission to download its contents.
  2. Uploaded the permitted first file to both buckets and attempted deletion. The delete failed because no identity-based policy allowed DeleteObject.
  3. Applied a bucket policy denying PutObject for the workload role on backup-bucket objects. Retested the same second file against both buckets.
  4. Applied the provided permissions boundary, then tested file3.txt and file4.txt against the data bucket.

Evidence

What I learned

An applicable explicit Deny overrides an Allow. For the identity permissions tested here, a boundary limits what the role policy can grant and does not grant access itself. Existing objects remain present when future uploads are restricted.

I also separated local command errors from authorization failures: an incorrect filename, path or shell-variable capitalization can fail before a meaningful AWS permission test occurs.

Validation limits. This was guided practice with assistant-supported troubleshooting. I did not test GetObject, Conditions, CloudTrail or every attached policy. The saved full boundary JSON was not separately captured; the file4 error provided functional evidence of its effect. These findings do not describe every possible resource-policy/session combination.
